# 搭把手订单状态机设计

## 当前状态

| 状态码 | 状态名称 | 允许的下一状态 |
|--------|----------|----------------|
| 0 | 已取消 | 无 |
| 1 | 待核销 | 3、0 |
| 2 | 已支付（旧流程） | 新订单不使用 |
| 3 | 服务中 | 5、6、7、0 |
| 4 | 待确认（旧流程） | 新订单不使用 |
| 5 | 已完成 | 7 |
| 6 | 已退款 | 0 |
| 7 | 争议中 | 5、6 |

新订单从货架或需求创建后进入状态 1。买家和卖家分别输入对方的开始核销码，双方完成后冻结买家积分并进入状态 3。双方再输入对方的完成确认码，全部完成后结算积分并进入状态 5。状态 3 的退款需双方同意；状态 3 或 5 可发起争议，由管理员仲裁至状态 5 或 6。

`OrderStatus.canTransitTo` 定义允许的状态边。旧流程的支付、开始服务、确认接口已不再作为新订单入口。当前定时任务只处理遗留的状态 4 订单，按 `order.confirm_timeout_hours` 配置自动结算，默认 72 小时。当前代码没有待核销超时自动取消或核销码超时自动退款任务。

接口请求及响应示例见 [订单 API 契约](../api/order.md)。
